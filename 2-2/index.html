    MODULE 2 | BUILD

    RUNNING, DEBUGGING, AND ITERATING

    i. WHAT YOU WILL DO

    Christopher Bienko (AI Enablement GTM Product Manager) provides an overview of the Build - Running, Debugging, and Iterating module for the hands-on enablement. [2 min]

    AI MATURITY CURVE

    Every fix in this chapter begins with evidence — a screenshot of the failing screen — and ends with your review of Bob's summary before the server restarts. Between those two points Bob works on its own. It diagnoses the problem and probes the backend with curl. It then edits the code and rebuilds. This is the discipline of the previous course applied to a live application. The investigation is delegated; the result is verified before it is trusted; the restart stays in your hands.

    A generated application is a starting point rather than a finished product. This chapter closes the gap.

    You start the teller portal Bob built and sign in. You then resolve the issues that surface: a login that fails, a page that looks plainer than the specification asked for, and a dashboard whose counters read zero. The method is the same every time:

    1. Take a screenshot and describe the problem in a sentence.
    2. Review what Bob changes before you restart.

    The chapter closes with the module's teller task, retrieving the balance for a specific IBAN through the portal you built.

    ii. WHY THIS MATTERS

    Generative AI produces a working application far faster than a team could write one. It also produces one with defects, because no specification can anticipate every runtime detail. A proxy behaves unexpectedly, a credential differs from what was assumed, or a token arrives late. The skill that matters in practice is the iteration loop, and it is a skill clients ask about directly: how does a practitioner fix what the agent got wrong without becoming an expert in the generated code?

    The answer this chapter demonstrates requires no reading of the source. A screenshot supplies the visual context and a plain-language sentence supplies the intent. Bob investigates from there. It reads its own code and tests the backend, then applies a fix that it explains. In a regulated industry setting, that explanation matters as much as the fix itself: each iteration leaves a record of what was wrong and what changed.

    iii. STARTING THE APPLICATION

    Bob's completion message from the previous chapter ends with the terminal commands needed to start the application. Your task for this module is to start the portal, sign in, and find the latest transactions for the client with IBAN DE89545769475769453536.

    Start the development server

    1. Scroll through Bob's final message until you find the terminal commands needed to start the front-end.

    2. Click Terminal in the top menu bar to open the terminal panel in the IDE.

    3. Click New Terminal to open a fresh terminal session in the project directory.

    4. Paste and execute the first terminal command Bob provided, for example:

      cd gfm-teller-app

      Your exact commands may differ depending on how Bob named the project directory.

    5. Paste and execute the next command Bob provided, typically the dependency install:

      npm install

    6. Paste and execute the final startup command Bob provided, typically:

      npm start

    7. Review the output for the URL where your application is running. In most cases this is localhost:3000.

    8. Navigate to the URL in your browser. The page may display a blank white screen for one to two minutes while the React application compiles and loads. This is normal; wait for it to finish before advancing along the lab steps.

    Find the credentials and sign in

    1. The GFM Bank — Teller Portal login screen appears and asks for credentials. Return to the Bob chat panel to find out where they are stored.

    2. Review Bob's completion message and look for a line mentioning login credentials. Bob may paste them directly in the chat or, as in this case, indicate that they are stored in an .env file in the project directory.

    3. Navigate to gfm-teller-app/.env in the file explorer sidebar.

    4. Open .env. It contains the REACT_APP_TELLER_USERNAME and REACT_APP_TELLER_PASSWORD values Bob configured during the build; these are the credentials for the application.

    5. Enter the username and password from .env into the login form and click Sign in. If you cannot locate the credentials, review Bob's output or check .env. You can also simply ask Bob for them.

    iv. THE DEBUG LOOP

    In the run captured here, two issues appear at once: the login attempt fails with a network error, and the login page looks plain despite the specification's instruction to use Carbon components. Both get fixed, starting with the login. You may or may not experience these issues; if your portal works, skip ahead to the next section.

    Fix the login error and the plain design

    1. When you encounter an error or want a UI improvement, the process is always the same.

      • Take a screenshot of the problem and paste it into Bob's Agentic Sidebar chat, then hit Enter to execute.
      • Be sure to describe the issue in natural, plain language (as if you were describing the problem to a colleague.)
      • Start by taking a screenshot of the entire page showing the login error.

    2. The screenshot captures both the network error and the plain design.

    3. Paste the screenshot directly into the Bob chat input so that Bob has visual context for what is going wrong.

    4. Alongside the screenshot, describe the issue in plain language — for example: "The login is failing with a network error, and the page design looks plain. Please fix both." No knowledge of the root cause is required; Bob reads the code, investigates, and resolves the issue on its own.

    5. Bob has already diagnosed the root cause.

      • The network error is a CORS issue: the login function calls the backend with the absolute BASE_URL through a bare axios.post, bypassing the dev-server proxy entirely. Bob requests permission to run a curl -s -X POST command against the backend to verify the actual API response.
      • Click Approve for task.

    6. The first curl command has run.

      • Bob now requests permission to run a second curl -si -X POST against the backend's /token endpoint with a different Authorization header, probing for the correct credentials.
      • Click Approve for task.

    7. The curl test confirmed that teller1/password1 returns Bad credentials from the backend.

      • Bob requests permission to run another curl -si against /token with a different header to discover the correct credentials.
      • Click Approve for task.

    8. Bob requests permission for one further curl -s -X POST against the /token endpoint. Click Approve for task.

    9. Bob has confirmed that the real credentials are teller / teller123.

      • It outlines a two-part fix: switch to relative URLs and update .env, then redesign the login header.
      • It updates .env with the correct credentials and begins reading LoginPage.js for the redesign.

    10. Bob has rewritten LoginPage.js with a Carbon-styled header and applied the matching SCSS changes.

      • It requests permission to run cd gfm-teller-app && npx react-scripts build 2>&1 to confirm that the updated application compiles cleanly.
      • Click Approve for task.

    11. The fix is complete.

      • Bob's message confirms the new credentials to use: username teller and password teller123.
      • A server restart is required for the changes to take effect.

    Restart the server and test the fix

    1. Click Terminal.

    2. Click New Terminal.

    3. In the terminal sidebar list, find the previously opened terminal labelled node — the terminal where the app is running — and click it to switch to that session. If you closed that terminal, simply run the same startup commands again.

    4. Identify the terminal where the application process is currently running; it shows active output from npm start or node.

    5. Press Ctrl+C in the running terminal to stop the development server. The prompt returns and accepts input again.

    6. Type npm start (or the startup command Bob originally provided) and press Enter to restart the application with the credential changes applied.

    7. Return to your browser and refresh the app URL. The page will remain on a white loading screen for a minute or more while the React build recompiles, which is expected.

    8. The app loads.

      A BROWSER WARNING YOU CAN DISMISS

      Some browsers warn that the password has appeared in a known data breach. This is expected, because the lab uses the simple demo credentials teller and teller123. The application runs locally and holds no real sensitive data. Close the warning and proceed.

    9. The login page design has been improved by Bob's fix: the Carbon components are styled correctly and the page now looks the part.

    10. Enter the new credentials (teller / teller123) and click Sign in.

    11. The design is fixed, but a network error still appears on sign-in. This needs a separate investigation.

    Resolve the remaining network error

    1. Take a screenshot of the page showing the network error, following the same process as before.

    2. Paste the screenshot into the Bob chat alongside a brief description of the problem, then hit Enter to execute.

    3. Bob investigates the network error, reading the API service files and environment configuration to find the root cause.

    4. Bob discovers that its previous fix to api.js was not persisted: the login() function still calls axios.post(${BASE_URL}/token, ...) directly, bypassing the dev-server proxy.

      • Bob has rewritten gfm-teller-app/src/services/api.js with a complete fix and requests permission to run cd gfm-teller-app && npx react-scripts build to confirm that the build still passes.
      • Click Approve for task.

    5. Bob requests permission to run cd gfm-teller-app && findstr /n "BASE_URL" to scan api.js for any remaining absolute BASE_URL references, confirming that the rewrite removed every direct backend call that bypassed the proxy. Click Approve for task.

    6. Bob confirms that the fix is complete. Review its summary to understand what changed.

    7. Another restart is required to apply this fix.

      • Depending on the nature of a fix, a restart may not be needed (sometimes a page refresh is enough), so review Bob's instructions each time.
      • As before, press Ctrl+C in the running terminal to stop the application.

    8. Type npm start and press Enter to restart the application.

    9. Enter the credentials and click Sign in again to test whether the network error is resolved.

    10. Sign-in succeeds and you reach the main dashboard. Two further issues are visible, however. The dashboard design still needs work. The Accounts counter reads zero, and so do the Customers and Balances counters.

    Improve the dashboard

    1. As before, take a screenshot of the dashboard showing the design you want Bob to improve.

    2. Paste the screenshot and type a plain-language prompt into the chat input.

      • For example: "Great, I can sign in now! Finally, lets add some nicer aesthetics to the teller portal, like you did for the login page."
      • When ready, hit Enter to execute.

    3. Bob responds with a plan for the visual uplift that sets out six goals, and then begins working. The goals cover the header and the side navigation. They also cover the page header and the metric tiles, followed by the quick-action tiles and the global spacing.

    4. Bob begins the visual improvements. Watch the terminal panel as the dev server at localhost:3000 automatically recompiles with the updated styles.

    5. Bob has verified the auth token flow and read index.scss to plan the uplift.

      • Bob requests permission to run a type command to read a temporary file as part of its CSS planning.
      • Click Approve for task.

    6. Bob has confirmed that the "teller" token is a bare string accepted as Bearer auth and has read the current index.scss.

      • Bob requests permission to run another curl -s against the backend to verify the token handling further before applying the visual changes.
      • Click Approve for task.

    7. Click Approve to allow Bob to proceed with the next change.

    8. Bob confirms that the API works with Bearer teller and that the "Forbidden" errors are a token-timing issue: the dashboard loads before the token propagates. It notes this as minor and continues planning before starting the visual work.

    9. Bob works through the remaining component updates.

    10. Bob has written the updated index.scss, AppShell.js, and DashboardPage.js with the full visual uplift. That covers a branded header and richer metric tiles.

      • Bob also adds quick-action cards and a token-timing fix.
      • It requests permission to run a Node.js command that verifies the new Carbon icons exist before triggering the build.
      • Click Approve for task.

    11. Bob has confirmed that all three required Carbon icons exist and requests permission to run cd gfm-teller-app && npx react-scripts build with a 300-second timeout to produce the final build with the visual changes applied. Click Approve for task.

    12. Bob's task is complete. The chat panel summarizes every change applied. There are quick-action tiles and section headings, along with a header carrying the BankMark SVG. The "Forbidden" fix in DashboardPage.js is listed as well. The dev server has already recompiled.

    13. Return to your browser, reload the app URL, and sign in again to see the updated design.

    Fix the empty dashboard counters

    1. Before the module's final task, address the remaining issue: the Accounts counter reads zero, and so do the Customers and Combined Balances counters.

      • A "Dashboard load failed — Forbidden" toast is also visible in the top-right corner.
      • The dashboard is not fetching its summary data from the backend correctly.

    2. As before, write a prompt describing the issue and attach a screenshot for context. Then hit Enter to execute.

    3. Bob identifies the zeros as an API response-shape mismatch and requests permission to run a curl -s command against the backend to determine the exact response structure before writing any fix. Click Approve for task.

    4. Tick I understand the risk and click Approve.

    5. Click Approve.

    6. Bob identifies three targeted fixes needed to resolve the zero-balance issue. Watch the Agentic Sidebar as it applies each one.

    7. Bob has applied the fixes to TransactionsPage.js, AccountsPage.js, and BalancesInquiryPage.js.

      • Bob adds token guards and makes the listCustomers API call fault-tolerant.
      • It also requests requests permission to run cd gfm-teller-app && npx react-scripts build to confirm that everything compiles with all three in place.
      • Click Approve for task.

    8. Bob finishes all three fixes. Review the completion message to understand what changed before restarting the app.

    9. Press Ctrl+C in the terminal to stop the running application.

    10. Run npm start to restart the application with the fixes applied.

    11. Return to your browser and sign in again. Your app may look different from the screenshots depending on what Bob generated, and your credentials may differ as well.

    12. The Total Accounts counter now shows 1,000, confirming that the fix worked. Customers and Combined Balances still read zero, which can be revisited later; the portion needed for the module's task is working, so the lab moves forward.

      FOR CLIENT ENGAGEMENTS

      When a demonstration needs every rough edge removed, continue iterating through the same loop — screenshot and plain-language prompt to the Agentic Sidebar — until the remaining counters populate. Module 3 closes with one more example of exactly this.

    v. COMPLETING THE TELLER TASK

    The front-end is running and you are signed in. What remains is the task set at the start of the module: find the latest transactions for the client with IBAN DE89545769475769453536.

    Look up the balance

    1. Click Balance Inquiry in the navigation menu to open the IBAN lookup form.

    2. On the Balance Inquiry page, enter the following IBAN into the input field and click Check Balance:

      DE89545769475769453536

    3. The inquiry succeeds and the account details for this IBAN are displayed, confirming that the teller portal is correctly connected to the backend and retrieving live customer data. Recall that this balance (€5,581.33) is the same value the Python teller client returned from the first prompt of this module; it is the balance you should receive on your attempt as well.

    vi. KEY TAKEAWAYS

    • A screenshot and a sentence are a complete bug report for Bob; no knowledge of the root cause is required to start an investigation.
    • Bob verifies before it edits: curl probes against the real backend established the true credentials and the true response shape before any code changed.
    • Read Bob's summary after every fix. It states whether a restart is required and records what changed, which is the trail a regulated environment expects.
    • Restarts remain a human action, and the white screen after one is the React build recompiling rather than a failure.
    • Not every defect must be fixed before moving on; decide which issues block the task at hand and defer the rest deliberately.
    • The balance retrieved through the portal matches the balance the Python client returned, which is the evidence that the generated front-end faithfully reaches the same backend.

    The teller portal is built, running, and proven against the live backend. In Module 3 | Secure, Bob turns from builder to reviewer, scanning the GFM Bank codebase for security vulnerabilities and working them through to remediation and verification.
