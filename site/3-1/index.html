    MODULE 3 | SECURE

    SECURITY ANALYSIS AND REMEDIATION

    i. WHAT YOU WILL SECURE

    Christopher Bienko (AI Enablement GTM Product Manager) provides an overview of the Secure - Security Analysis and Remediation module for the hands-on enablement. [4 min]

    AI MATURITY CURVE

    This closing module extends Bob's reach to reviewing the code it has been working with all along. The documents it produces — the audit report, the deep dive, and the verification — are the record a regulated environment requires of any change to a system that handles money. Your control remains where it has been throughout. Each fixed file waits for your approval before it is written. The verification report is something you read and judge rather than accept on its word.

    The first two modules had Bob understand the GFM Bank system and build on top of it. This module turns Bob into the system's reviewer. You direct it through a vulnerability scan of the codebase, classified against the OWASP Top 10 and CWE. You will afterwards have Bob produce a formal security audit report and a deep dive on the five most critical findings. Finally, Bob will apply the remediations and write a verification report confirming that the fixes have held. A final run of the teller portal confirms that the patches did not break any functionality or systems.

    ii. WHY THIS MATTERS

    Security review is where a regulated industry's expectations are most explicit. A finding is expected to carry a classification and a severity. It must name a location and an attack scenario. It must also propose a remediation and that remediation is expected to be verified rather than assumed. Producing that material by hand is slow work, which is why it so often arrives late, after the code has shipped.

    Bob compresses the cycle into a single session. It scans the code and ranks what it finds. It documents the findings and fixes them, then it verifies the result. Each stage is left behind as a file you can hand to an auditor for deeper review and inspection. Whether a finding is accepted, deferred, or challenged remains a judgment left to the human-in-the-loop. This practice mirrors the review-first, trust-later discipline of this entire hands-on lab applied to scenarios where the consequences for failure are highest.

    iii. SCANNING FOR VULNERABILITIES

    The scan runs in a fresh session so that Bob's context holds only the security work rather than the state left over from the previous modules.

    Prepare a clean session

    1. Return to IBM Bob and stop any open terminal processes by pressing the Kill (garbage-can) button in the terminal panel.

    2. Press the + button to open a new chat window. A fresh chat gives Bob a clean context window, without the state from Modules 1 and 2, which keeps the security analysis focused.

    3. As a reminder, confirm that you are in Agent mode. If you are comfortable doing so, confirm as well that the Auto-approve permissions are enabled as directed in Module 1.

    Run the vulnerability scan

    1. Paste the following prompt and hit Enter to have Bob perform a comprehensive security vulnerability scan of the codebase:

      Analyze the code files in this project for security vulnerabilities. Identify all security issues, categorize them by type (OWASP Top 10, CWE), and rank them by severity (Critical, High, Medium, Low).

For each vulnerability found, provide:

- Location (file and line number)
- Vulnerability type and category
- Description of the security risk
- Potential attack scenario
- Severity rating with justification

    2. Bob starts working, reading through the Python backend files to identify vulnerabilities and classifying them against the OWASP Top 10 and CWE frameworks.

    3. Bob completes the scan. The analysis may take a minute or two; wait for it to finish before proceeding.

    4. Scroll through the initial portion of Bob's findings and continue reading the full analysis output.

    5. Finish reading the full security analysis. Make a note of the critical and high-severity findings, which are addressed in the sections that follow.

    iv. DOCUMENTING THE FINDINGS

    The scan lives in the sidebar. The next two prompts turn it into the documents a review process expects: a structured audit report and a detailed treatment of the most serious findings.

    Generate the security audit report

    1. Paste the following prompt and hit Enter to have Bob generate a structured security audit report:

      Generate a comprehensive SECURITY_AUDIT_REPORT.md document that includes:

 1. **Executive Summary**

    - Overview of files analyzed
    - Total vulnerabilities found by severity
    - Overall risk assessment
    - Key recommendations

 2. **Vulnerability Inventory**
    For each vulnerability:

    - Unique ID (e.g., VULN-001)
    - File and line number
    - Vulnerability title
    - CWE/OWASP classification
    - Severity rating (Critical/High/Medium/Low)
    - CVSS score estimate (if applicable)
    - Detailed description
    - Proof of concept / attack scenario
    - Business impact
    - Remediation recommendation
    - Remediation effort estimate

 3. **Risk Matrix**

    - Visual representation of vulnerabilities by severity and likelihood

 4. **Remediation Roadmap**

    - Prioritized list of fixes
    - Suggested implementation order
    - Dependencies between fixes

 5. **Secure Coding Guidelines**

    - Best practices to prevent similar issues
    - Language-specific recommendations for Python

Save this as SECURITY_AUDIT_REPORT.md in the current directory.

    2. Bob may attempt to generate the entire report in a single pass, which can take several minutes. Wait for the task to complete.

      IF BOB STOPS MID-GENERATION

      If Bob appears to time out or stop part-way through the report, send the prompt continue to resume from where it left off.

    3. When the report is finished, click SECURITY_AUDIT_REPORT.md in the file explorer sidebar to open it.

    4. Right-click the file tab and select Open Preview to view the report with full Markdown formatting applied.

    5. Review SECURITY_AUDIT_REPORT.md. Bob has produced a professional audit document covering every vulnerability found, its severity, and the recommended remediation.

    Produce the deep dive

    1. Paste the following prompt and hit Enter to have Bob produce a detailed treatment of the five most critical vulnerabilities:

      For the top 5 most critical vulnerabilities found, create detailed documentation that includes:

 1. **SQL Injection in data_pipeline.py**

    - Show the vulnerable code
    - Explain why it's vulnerable
    - Demonstrate a potential exploit
    - Show the secure fix using parameterized queries

 2. **Command Injection vulnerabilities**

    - Identify all instances of shell=True
    - Explain the risks
    - Provide secure alternatives using subprocess with lists

 3. **Insecure Deserialization (pickle)**

    - Explain the remote code execution risk
    - Show how an attacker could exploit this
    - Recommend safe alternatives (JSON, safe serialization)

 4. **Hardcoded Secrets**

    - List all hardcoded credentials and secrets
    - Explain the risks of exposure
    - Show how to use environment variables or secret managers

 5. **Cryptographic Weaknesses**

    - Identify weak hashing (MD5) and insecure randomness
    - Explain why these are insufficient for security
    - Provide modern, secure alternatives

    2. Bob starts on the deep-dive documentation, reading the relevant source files and producing detailed exploit scenarios and remediation guidance.

    3. Bob is typically able to complete this in a single pass. When it finishes, VULNERABILITY_DEEP_DIVE.md appears in the project explorer.

    4. Right-click VULNERABILITY_DEEP_DIVE.md and select Open Preview to review the formatted document.

    5. Review the deep dive. Bob has identified real security flaws in the codebase, each with a concrete exploit demonstration and a secure-code fix.

    6. Continue scrolling through the document to read all five vulnerability sections and their recommended fixes.

    v. REMEDIATING AND VERIFYING

    With the findings documented, Bob applies the fixes and then reviews its own work. Each fixed file waits for your approval before it is written.

    Apply the fixes

    1. Paste the following prompt and hit Enter to have Bob apply the security fixes to the codebase:

      Fix all security vulnerabilities in the codebase. For each fix:

- Apply the secure coding pattern
- Add comments explaining the security improvement
- Ensure the fix doesn't break existing functionality
- Follow Python security best practices

Specifically:

- Replace string formatting in SQL with parameterized queries
- Replace shell=True with subprocess using argument lists
- Remove or externalize hardcoded credentials
- Replace pickle with JSON for serialization
- Enable SSL verification in requests
- Fix file permissions to restrictive values (0o600)
- Replace MD5 with SHA-256 or bcrypt for password hashing
- Use secrets module instead of random for tokens
- Remove eval/exec or implement strict sandboxing
- Use secure JWT configuration with external secrets

Create the fixed versions of:

- data_pipeline_secure.py

    2. Bob starts applying the fixes. Because it already read the relevant files in the previous prompts, it proceeds directly to the remediation without re-reading the code.

    3. Click Approve for task to allow Bob to write the first fixed file.

    4. Click Approve for task to allow Bob to write the next fixed file.

    5. Click Approve for task to allow Bob to write the final fixed file.

    6. Bob finishes applying the fixes. Review the completion message in the Agentic Sidebar to see what changed in each file.

    Verify the remediation

    1. Paste the following prompt and hit Enter to have Bob verify the fixes and produce a final remediation verification report:

      Review the fixed code files and verify that:

- All identified vulnerabilities have been addressed
- No new security issues have been introduced
- The code still functions correctly
- Security best practices are followed

Generate a REMEDIATION_VERIFICATION.md document that includes:

- Checklist of all vulnerabilities and their fix status
- Any remaining concerns or recommendations
- Suggestions for additional security hardening
- Recommendations for security testing (SAST, DAST, penetration testing)

    2. Bob starts reviewing the fixed files. Click Approve for task when the approval dialog appears.

    3. Click Approve for task to allow Bob to proceed with reading and verifying the fixed files.

    4. Click Approve for task to allow Bob to write the verification report.

    5. Bob confirms that REMEDIATION_VERIFICATION.md has been written to the project directory. Open it to review.

    6. Right-click the file tab and select Open Preview to read the verification report in formatted Markdown.

    vi. CONFIRMING THE APPLICATION STILL WORKS

    A remediation that breaks the application is a defect of its own. As a final sanity check, restart the teller portal and confirm that it still runs against the patched backend code.

    Restart the application

    1. If you have lost track of the startup commands after so many prompts, ask Bob in natural language — for example, "How do I start the frontend?" or "What commands do I run to start the GFM teller app?"

    2. Bob understands the question and provides the exact terminal commands needed to start the application again.

    3. Run the startup commands in the terminal to restart the application and confirm that it works correctly after the security fixes.

    4. Sign in again and reach the dashboard. As expected, the application still works.

      WHAT YOU HAVE COMPLETED

      At this point you have completed all three modules of the lab. Because Bob is powered by generative AI, your banking application may look different from the screenshots, and the exact issues you encountered may have varied. What matters is that you have worked the full cycle: codebase analysis in Module 1, a Carbon-based React front-end in Module 2, and vulnerability detection and remediation in Module 3.

    Optional: apply the remaining polish

    For client engagements, or simply for a clean demonstration, the remaining zero-balance counters on the dashboard can be resolved with the same loop used throughout Module 2.

    1. Take a screenshot of the dashboard and send it to Bob with a plain-language description of the problem.

    2. Work through the approval flow in the Agentic Sidebar as usual. Bob investigates the cause, applies the fix, and confirms when it is complete.

    3. Depending on what Bob changed, you may or may not need to restart the development server. If prompted, run npm start in the terminal following the same process used throughout the lab.

    4. Reload the browser and confirm the fix. If the issue is not fully resolved on the first attempt, continue iterating as you have done throughout this lab: take a screenshot and describe the problem, then let Bob work on it.

    vii. WRAPPING UP

    Before concluding, dwell a moment longer on your results and findings across Module 3:

    • A fresh chat session keeps the security analysis focused; context from earlier modules is left behind deliberately.
    • Classifying findings against the OWASP Top 10 and CWE, and ranking them by severity, turns a scan into something a review board can act upon.
    • The three documents — the audit report, the deep dive, and the remediation verification — are the record of the work. Each is a file in the workspace rather than a conversation that scrolls away.
    • Bob applies fixes and then verifies its own work, but each written file passes through your approval and the verification report is yours to judge.
    • Long generations can stall; the prompt continue resumes them.
    • A remediation is complete only once the application has been restarted and proven to work, and the iteration loop remains available for whatever polish a demonstration needs.

    Congratulations on reaching the end of the hands-on work and exercises. Across the three modules, Bob has taken GFM Bank from an unfamiliar codebase to a documented, extended, and hardened system.

    • Module 1 produced the written understanding: an architecture reference, a data-pipeline analysis, a functional requirements document, and a catalogue of the invariants the system must never violate.
    • Module 2 turned that understanding into a working Carbon teller portal generated from a single specification. It was then repaired through screenshots and plain-language prompts until it returned the same balance the original Python client did.
    • Module 3 closed the loop with a vulnerability scan classified against the OWASP Top 10 and CWE. That scan became an audit report and a deep dive on the five most critical findings, followed by remediations and a verification report that confirmed the fixes held.

    At every one of those stages, you reviewed and approved before anything was trusted. That pairing is the discipline of the AI Maturity Curve exercised on a system that handles money, and it is the story to bring to your next conversation with a client in a regulated industry.
