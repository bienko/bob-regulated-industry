    MODULE 2 | BUILD

    BUILDING THE CARBON TELLER FRONT-END

    i. WHAT YOU WILL BUILD

    Christopher Bienko (AI Enablement GTM Product Manager) provides an overview of the Build - Building the Carbon Teller Front-End module for the hands-on enablement. [2 min]

    AI MATURITY CURVE

    This chapter is Module 2 | Delegate at project scale. One specification produces an entire application, and an approval gate precedes every consequential step. The specification also grounds Bob deliberately. It requires that every Carbon prop name and token come from the local .d.ts files rather than from memory, which is the context-quality discipline of Module 4 | Scale & Extend applied to a design system. The result is code that maps onto the real backend and the real component library.

    The previous module left you with a documented understanding of GFM Bank. This module puts it to use. You first prove that the existing Python teller client can reach the live GFM Bank backend and return a real account balance. You then hand Bob a single, detailed specification and have it generate a complete React teller portal on the IBM Carbon Design System, grounded in the offline Carbon references shipped with the workspace. By the end of the chapter the portal is built and its dependencies are installed with a clean compile.

    ii. WHY THIS MATTERS

    A front-end for a regulated system has two obligations that ordinary web applications can afford to relax.

    1. It must call the real backend, with its real endpoints and roles and validation rules. A teller interface that drifts from the core banking API is a compliance problem in its own right.
    2. It must also present a consistent, accessible interface that an institution can standardize on, which is why the specification insists on the IBM Carbon Design System.

    Both obligations are met the same way: by grounding Bob in authoritative local sources before it writes a line of code. The Python clients from Module 1 describe the API as it actually is. The carbon-offline-reference folder describes the component library as it actually is. The specification directs Bob to read both, and the build you observe in this chapter is the consequence.

    iii. PROVING THE BACKEND CONNECTION

    ATTENTION: NON-DETERMINISTIC WORK AHEAD

    The sequence of commands and approvals in this section is specific to the run captured in the screenshots, which was performed on Windows with PowerShell. Depending on your operating system and Bob version, the issues you encounter will differ, and you may encounter none at all. In every case Bob works toward a viable alternative on its own. Where it does not, a plain-language description of the problem is enough to move it forward. Later chapters demonstrate this.

    Before building anything new, confirm that the existing teller client can reach the live backend. The exchange also shows how Bob works through environment-specific failures on its own.

    Start a new task and send the test prompt

    1. Open a new chat window by clicking the + button.

    2. Paste the following prompt into the Agentic Sidebar chat input and hit Enter to test the teller client against the live backend server:

      Can you test my teller client with my server:
https://wxo-corebanking-backend.1944johjccn7.eu-de.codeengine.appdomain.cloud/docs

Use IBAN DE89545769475769453536 to check the balance
      CONNECTIVITY ISSUES?

      The database and transactions supporting the wxo-corebanking-backend server resets every 60 minutes to its default stage to ensure that the environment is properly maintained. Resets to the server take approximately 1 minute to resolve. If you are experiencing connectivity issues, wait a few minutes and try again. If it continues to fail, reach out to the documentation authors for support.

    3. Bob starts working, reading the teller client code and connecting to the backend server to run the balance inquiry.

    Work through the approval loop

    1. Bob requests permission to run an Execute Command that sets the COREBANK_URL environment variable and runs the teller client script against the live backend. Click Approve for task to allow it.

    2. In this example, the first command failed (exit code 1) because a trailing space in the URL caused set to encode it as %20.

      • Bob explains the issue and requests permission to retry with a corrected PowerShell command that runs python teller_client.py directly from the code directory.
      • Click Approve for task.

    3. The second attempt also failed (exit code 1): the cd path was not resolving correctly.

      • Bob now requests permission to run python directly with the full path to teller_client.py from the workspace root.
      • Click Approve for task.

    4. The previous runs defaulted to localhost because the environment variable was not being passed through correctly.

      • Bob requests permission to run a PowerShell command that sets $env:COREBANK_URL inline before calling python teller_client.py, so that the remote URL is picked up.
      • Click Approve for task.

    5. That command failed because the backend server took longer than 10 seconds to respond.

      • Bob reports that DNS resolved and the TLS handshake completed — the server is simply slow to start — and requests permission to retry with a 90-second timeout.
      • Click Approve.

    6. Bob now requests permission to run a PowerShell command that sets $env:COREBANK_URL inline and runs the teller client with a TIMEOUT = 60 override, giving the cold-starting backend more time to respond. Click Approve for task.

    7. After several failed attempts, Bob has sought out an alternative on its own: it has written a _test_teller.py helper script to isolate the connection test and requests permission to run python _test_teller.py with a timeout_seconds: 180 override. Click Approve for task.

    8. The helper script ran successfully and returned live transaction data from the backend — multiple PAYMENT records with account IDs, timestamps, and EUR amounts.

      • Bob confirms that everything works and requests permission to delete the temporary file (del _test_teller.py).
      • Click Approve for task to let it clean up.

    9. Bob deletes the temporary file and delivers the result: the teller client connected successfully.

      • It displays the summary for IBAN DE89545769475769453536: the account ID and customer ID, together with a current balance of €5,581.33.
      • Below them are the latest five ledger rows with booking timestamps and EUR amounts.
      • Record that balance to a notepad, as you will meet it again at the end of the next chapter.

    iv. GENERATING THE TELLER PORTAL

    With the backend proven reachable, hand Bob the specification for the front-end. It is a long prompt by design. It names the backend and the credentials. It lists every teller operation to replicate and the Carbon components to use. It also sets out the technical and security requirements to honor.

    Start a fresh task

    1. In the Bob IDE, locate the IBM BOB panel on the right side of the screen.

      • Click the New Task button (the + icon in the top-right corner of the panel) to open a fresh task session.
      • A new task gives Bob a clean context window, free from the previous conversation.

    2. Before submitting the prompt, confirm once again that Bob is set to Agent mode; the Agent toggle is visible at the bottom-left of the panel. If you are comfortable with it, confirm that the Auto-approve permissions are enabled as well.

    Send the specification

    1. Copy and paste the following prompt into the Agentic Sidebar. It instructs Bob to build a comprehensive React-based teller front-end for GFM Bank using the IBM Carbon Design System, referencing the local Carbon component .d.ts files for accurate API shapes:

      Before beginning implementation, read carbon-offline-reference/CARBON_REFERENCE.md to locate the .d.ts path for every Carbon component you plan to use, then read each of those .d.ts files. All prop names, valid values, design token names, and icon names must come from those local files — do not use memory or any external source for Carbon API shapes.

Create a comprehensive React-based Teller Front-End application for GFM Bank using IBM Carbon Design System with the following specifications:

Application Requirements:
- Develop a modern, professional banking teller interface that connects to the Core Banking backend server at https://wxo-corebanking-backend.1944johjccn7.eu-de.codeengine.appdomain.cloud/docs

Authentication System:
- Implement a secure login page with IBM Carbon form components
- Store credentials in environment variables (.env file): username "teller" and password "teller123"
- Include proper form validation and error handling
- Add session management with secure token storage

Main Dashboard Layout:
- Display "GFM Bank" branding prominently in the header using IBM Carbon design tokens
- Position a real-time backend server status indicator in the top-right corner showing "Online" (green) or "Offline" (red/gray) with automatic health check polling
- Implement IBM Carbon's UI Shell component for consistent navigation and layout

Teller Operations Interface:
- Replicate all functionality from the teller_client.py with modern UI components:

- Account balance inquiry with IBAN input and formatted currency display
- Customer account creation form with validation
- Money deposit interface with amount input and transaction confirmation
- Money withdrawal interface with balance verification
- Account-to-account transfer with dual IBAN inputs and amount specification
- Transaction history viewer with sortable, filterable data tables
- Account details lookup with comprehensive information display

Design Considerations:
- Before writing any code, read carbon-offline-reference/CARBON_REFERENCE.md and the .d.ts file for every component you intend to use. Use only prop names and values found in those files. Do not rely on memory for any Carbon prop shape.
- Apply IBM Carbon banking theme with professional color palette (blues, grays, whites).
- Use only token names listed in the Design Token Quick-Reference table in CARBON_REFERENCE.md — written as var(--cds-) in CSS. Never use removed v10 token names (brand-01, ui-01, ui-02) or the bx-- CSS prefix.

- Use Carbon's data table components for transaction lists and account information
- Implement Carbon notifications for success/error messages
- Add loading states using Carbon skeleton components during API calls
- Ensure responsive design for various screen sizes
- Include proper error boundaries and fallback UI
- Add confirmation modals for critical operations (withdrawals, transfers)
- Display currency amounts with proper formatting (EUR symbol, decimal places)
- Implement form validation with real-time feedback
- Add accessibility features (ARIA labels, keyboard navigation)

Technical Implementation:
- Use React functional components with hooks
- Implement Axios or Fetch for API communication
- Add environment variable configuration for backend URL and credentials
- Add a "proxy" field in package.json pointing to the backend URL so the dev server forwards API requests and avoids CORS errors in the browser
- Include proper TypeScript types or PropTypes validation
- Structure components logically (pages, components, services, utils)
- Implement React Router for navigation between views
- Add state management (Context API or Redux) for user session and app state
- Include automated backend health checks with configurable intervals
- Handle API errors gracefully with user-friendly messages

Security Features:
- Implement JWT token handling if applicable
- Add automatic logout on session expiration
- Sanitize all user inputs
- Use HTTPS for all API communications
- Implement CORS handling via the dev server proxy — do not hardcode the backend URL as the axios baseURL in development

Additional Features:
- Add a dashboard summary showing key metrics
- Include quick action buttons for common teller operations
- Implement search functionality for customer accounts
- Add print receipt functionality for transactions
- Include audit trail logging for compliance

Provide complete, production-ready code with proper project structure, package.json with all dependencies (react, @carbon/react, react-router-dom, axios, dotenv), and clear setup instructions.

    2. With the prompt pasted into the Agentic Sidebar, hit Enter to execute the instructions.

    Watch Bob ground itself in the Carbon references

    1. Bob begins working immediately. As instructed, it first reads carbon-offline-reference/CARBON_REFERENCE.md. It then expands to read the individual Carbon component .d.ts files. These are TypeScript declaration files that describe each component's exact props and API surface. Among the components it reads are SideNavLink and Header, then SideNav and HeaderName, along with DataTable and others. This reading phase is what allows Bob to generate accurate component code rather than inventing prop names from memory.

    2. Having finished reading the Carbon .d.ts files, Bob announces that it has everything it needs and moves on to understand the workspace layout. It lists files in bob-banking-lab and in bob-banking-lab/LABs, and then in the Banking Industry folder.

    3. Bob continues working through its plan. It has listed the full bob-banking-lab/LABs directory tree, read the existing Teller Application lab files, and is reading teller_client.py to understand every API endpoint the new front-end will need to call.

    4. Bob has finished its discovery phase and produced a complete map of the GFM Bank backend API. The Agentic Sidebar lists every endpoint it found by reading the Python client files:

      • POST /token (login)
      • GET /accounts
      • GET /transactions/{account_id}
      • POST /transfer
      • GET /customers
      • POST /transactions/{account_id} (deposit and reversal)
      • PATCH /accounts/{account_id}/overdraft

      This discovery step is what ensures the generated front-end maps exactly onto the real backend rather than onto a generic template that would need manual correction.

    Approve the build steps

    1. Bob reaches its first approval checkpoint. After declaring that it is ready to build, it attempted to write teller-ui/package.json, but the target directory did not yet exist.

      • Bob now requests permission to run a shell command to create the folder.
      • Click Approve for task to allow Bob to create the directory and continue.

    2. Progress is visible: the mkdir command ran, package.json was written, and two additional files were edited. Note the green change indicator on bob-banking-lab in the file explorer — Bob is actively writing files to your workspace. Bob has also encountered a limitation: creating the public/ sub-directory failed because the file-write tool cannot handle spaces in deeply nested folder paths.

      • Bob self-corrects and requests permission to run a cd command to navigate into the new directory before creating sub-directories.
      • In the Tools awaiting approval panel, click Approve for task.

    3. The first cd command has run, and a second Execute Command approval is waiting for another cd deeper into the project structure. Click Approve for task again.

    4. Bob requests permission to write public/index.html using a PowerShell Set-Content command, to avoid path-handling issues with special characters and spaces.

      • The Tools awaiting approval panel shows the request, containing the complete HTML boilerplate for the GFM Bank Teller Portal.
      • Click Approve for task.

    5. That command exited with code 1 because of PowerShell quote-escaping syntax.

      • Bob immediately self-corrects and formulates a refined PowerShell script that uses a $content variable to write public/index.html safely.
      • Click Approve for task.

    6. To handle workspace paths with spaces and special characters reliably across platforms, Bob switches to a Python script using pathlib. The script creates every target sub-directory and writes public/index.html. The sub-directories are:

      • public
      • src
      • src/pages
      • src/components
      • src/context
      • src/services
      • src/utils

      Click Approve for task to run it.

    7. After the directory-creation script executes, Bob runs a verification script using BASE.iterdir() to confirm that the target directory and sub-directories exist before proceeding. Click Approve for task.

    8. Bob determines that writing a dedicated Python script file and executing it will be the cleanest way to generate the remaining application code across the folder hierarchy. The Agentic Sidebar shows it changing approach: "Let me try a different approach — write a Python script file first and then execute it."

    9. Bob pauses to inspect the current state of the project folder with a dir command before running its generator. Click Approve for task.

    10. The directory check succeeds. Bob confirms that the target directories exist and begins writing a Python generator script designed to produce all of the application's source files at once.

    11. Bob has written scripts/generate_teller_ui.py and requests permission to execute it with python scripts/generate_teller_ui.py.

      • Because running a newly generated script triggers a security confirmation, a Security warning notice appears.
      • Tick the I understand the risk checkbox, then click Approve to run the script and generate the complete front-end codebase.

    12. With the generator script approved and running, Bob scaffolds the full set of application components and service layers.

    13. Bob has generated all source files, verified them, and written the project README.md.

      • Bob now begins final validation by preparing to run npm install inside the new UI directory to ensure all dependencies resolve cleanly.
      • In the Tools awaiting approval panel, click Approve for task.

    14. With all npm packages installed, Bob is ready for the final build check, which verifies that the React code compiles with no TypeScript or syntax errors. Click Approve for task to run the build.

    Review what was built

    1. The task is complete. The top of the Agentic Sidebar displays a green All tasks completed! badge with the sub-task counter, confirming that every planned step finished. Below it, Bob presents a What was built summary with a File map table listing each generated file alongside its purpose. Key files include:

      • package.json — the dependencies and the proxy to the backend URL
      • .env — the teller credentials via REACT_APP_TELLER_USERNAME and REACT_APP_TELLER_PASSWORD
      • src/index.scss — Carbon imports and custom CSS variable overrides
      • src/services/api.js — an Axios instance with a Bearer-token interceptor and auto-logout on 401
      • src/context/AuthContext.js — session state via sessionStorage with login() and logout()

      The teller front-end has been generated from a single prompt. It is mapped onto the real backend and built against the real Carbon library.

    v. KEY TAKEAWAYS

    • Prove the backend before building on it: the teller client's successful balance inquiry establishes the ground truth the front-end must reproduce.
    • Environment-specific failures are normal in agentic work, and Bob works through them by explaining each one and proposing an alternative; your role is to read the explanation before approving.
    • A long, explicit specification is what makes a one-prompt build reliable. It names the backend and the operations, then the components and the constraints, so that Bob is not left to guess.
    • Grounding Bob in local references (the Python clients and the Carbon .d.ts files) produces code that matches the real API and the real component library.
    • Security warnings on newly generated scripts are gates you clear deliberately, after reading what the script will do.
    • The build ends with a file map and a clean compile. From there the application is yours to run and to judge.

    The application is built, but has not yet been run. In Running, Debugging, and Iterating, you start the development server and sign in. You then work through the issues that surface with a screenshot and a sentence, reviewing Bob's fix each time, before completing the module's teller task.
