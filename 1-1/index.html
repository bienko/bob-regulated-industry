    MODULE 1 | ANALYZE

    UNDERSTANDING THE CORE BANKING CODEBASE

    i. WHAT YOU WILL ANALYZE

    Christopher Bienko (AI Enablement GTM Product Manager) provides an overview of the Analyze - Understanding the Core Banking Codebase module for the hands-on enablement. [2 min]

    AI MATURITY CURVE

    The discipline of this module is the one you practiced throughout the previous course: understand before changing. Here it applies to a system that handles money. Your control sits in two places. You decide whether to enable auto-approval, and you review each document Bob writes before it is trusted. The documents themselves follow the persistent-artifact pattern of Module 4 | Scale & Extend: understanding captured once and reused by every later conversation.

    Before a single line of the GFM Bank application is changed, it must be understood. In this module you direct Bob through a series of read-only analyses of the codebase. Each produces a persistent document in the workspace: first an architecture reference and then a data-pipeline analysis. A functional requirements document and a catalogue of the system's invariants follow. Nothing in the application is modified. What you leave behind is the written understanding that every later module builds upon.

    ii. WHY THIS MATTERS

    In a regulated environment, the questions an auditor asks of a system are the same questions an engineer must answer before changing it. What does each role have permission to do? Which rules govern a transfer, an overdraft, or a fee reversal? What must always remain true in the database, and where in the code is that guaranteed? Answering these by reading source files across a codebase is slow, and the answers rarely get written down.

    Bob compresses that discovery work into a handful of prompts. It writes the answers into documents for longevity and maintainability. Those documents serve two purposes at once. They give you the mental model needed for the build work in Module 2. They also form the first entries in the written record that regulated industries require of any system they operate.

    iii. ANALYZING THE CODEBASE

    You will send Bob six prompts in sequence. The first four produce the reference documents; the remaining two extract the requirements and the invariants. All of them are read-only tasks.

    Confirm Agent mode and permissions

    1. Before sending any prompts, confirm that Agent mode is selected. Click the mode selector in the bottom-right corner of the Bob panel and choose Agent from the dropdown.

    2. Click the Permissions button at the bottom of the Bob panel. If you wish, enable the Auto-approve toggle so that every permission group is checked:

      • Read
      • Edit
      • Execute
      • MCP
      • Skill
      • Todo
      • Subtask
      • Subagent
      • Mode

      A WORD ON AUTO-APPROVE

      Enabling auto-approval prevents Bob from pausing to ask for manual approval on every individual file read or tool call, which keeps the lab moving. It is a convenience rather than a requirement: if you would rather review Bob's actions individually, leave the toggle unchecked and approve each request as it arrives. You can change the setting at any point in the lab. Either way, the decision about how much autonomy to grant remains yours — the same control you exercised throughout the previous course.

    Analyze the codebase

    1. Paste the following prompt into the Bob chat input. It asks Bob to perform a deep, read-only analysis of the GFM Bank core banking codebase — no code is changed at this stage. Bob reads through the project files and produces a structured explanation along with Mermaid diagrams (a text-based diagramming format used to visualize architectures and data flows.)

      Analyze the GFM Bank Core Banking codebase and provide a comprehensive explanation of its functionality, including:

- **API Architecture**: How the FastAPI backend handles authentication (OAuth2), account management, and transaction processing
- **Role-Based Access Control**: How TELLER and BACKOFFICE roles differ in their permissions and capabilities
- **Transaction Processing**: The transfer logic including balance verification, overdraft handling, and the two-transaction debit/credit pattern
- **Data Model**: The relationship between users, customers, accounts, and transactions tables
- **Client Applications**: How teller_client.py and backoffice_client.py interact with the API

Additionally, create detailed Mermaid diagrams showing:

- System architecture with all components
- API endpoint structure and authentication flow
- Transaction processing sequence
- Data model relationships

Clearly state key invariants, business rules, and assumptions made by the code.
      • After pasting, the prompt collapses in the chat input into a grey pill labelled "Pasted text #1 - xx lines".
      • In this example it pasted as 16 lines; formatting differences may give you a different count, which is fine as long as the prompt itself is intact.
      • You can click the pill to expand and review the full prompt before sending.

    2. Click the "Pasted text #1 - xx lines" pill to open a popup showing the full prompt.

      • Verify that the pasted content matches the prompt above, then click Save to close the popup and return to the chat input.
      • This review step ensures you send exactly the instructions you intend.

    3. Click the Send button (the arrow icon in the bottom-right corner of the chat input) or hit Enter to submit the prompt.

    4. Bob begins working immediately. Because this prompt involves only read-only actions, little or no manual approval should be needed. Bob reads through the project directory and produces a structured explanation; you can watch its progress in the panel as it works through each file.

    5. When the analysis is complete, take a few minutes to read through Bob's response.

      • This is where your mental model of the GFM Bank application forms, before anything is changed in the modules ahead.
      • It covers the architecture and the roles. It also covers the transaction logic and the data relationships.

    6. Scroll down through the response to read the complete analysis. It includes the Mermaid diagrams Bob generated: one for the system architecture and one for the API flow, followed by the transaction sequences and the data model relationships.

    Produce the architecture document

    1. Now ask Bob to turn its analysis into a permanent architectural reference. Paste the following prompt into the chat input:

      Based on your analysis, create a comprehensive ARCHITECTURE.md document that includes:

 1. **Executive Summary**: One-paragraph overview of the system
 2. **System Architecture**: High-level Mermaid diagram showing all components
 3. **Component Descriptions**: Detailed explanation of each module
 4. **API Reference**: All endpoints with their purposes and access controls
 5. **Data Model**: Entity-relationship diagram using Mermaid
 6. **Transaction Flow**: Sequence diagram for key operations (transfer, balance inquiry)
 7. **Security Model**: Authentication, authorization, and data protection
 8. **Functional Requirements**: List of supported business operations
 9. **Non-Functional Requirements**: Performance, reliability, and scalability considerations
 10. **Assumptions and Constraints**: Technical and business limitations

Save this as ARCHITECTURE.md in the current directory.

    2. As before, you can click the "Pasted text #1 - xx lines" pill to expand and verify the full prompt.

      • From this point on, the pasted-text pill will not be shown again for every prompt, but the process is always the same.
      • Click the pill and review the content, then press Save to confirm.

    3. Click Save to close the popup and return to the chat input, then hit Enter to submit the prompt.

    4. Bob begins writing the ARCHITECTURE.md file.

      • This task involves writing a new file, so Bob uses its edit tools to create the document directly in the project directory.
      • Watch the panel for progress updates as it works through each section.

    5. Bob confirms that it has created the document. Click ARCHITECTURE.md in the file explorer sidebar to open it.

    6. Review the contents. Bob has produced a structured reference document covering all of the sections you specified, from the executive summary through to the assumptions and constraints.

    Analyze the data pipeline

    1. Now ask Bob for a deeper analysis of the transaction processing pipeline. Paste the following prompt into the chat input:

      Create a detailed data pipeline analysis that covers:

- **Request Lifecycle**: From HTTP request to database commit
- **Transaction States**: How transfers move through validation, execution, and confirmation
- **Error Handling**: What happens when transactions fail at each stage
- **Consistency Guarantees**: How the system ensures ACID properties
- **Audit Trail**: What information is logged and stored for compliance

Include a Mermaid flowchart showing the complete data pipeline from client request to persisted transaction.

      This prompt is shorter, so it is sent directly rather than collapsed into a pasted-text pill.

    2. Click the Send button (or hit Enter on your keyboard) to submit the data pipeline analysis prompt.

    3. Bob begins working on the analysis. Watch the Agentic Sidebar as it reads through the project files and constructs the flowchart and supporting documentation.

    4. When complete, Bob confirms it has written DATA_PIPELINE.md to the project directory. Read through the summary in the panel to see what was documented.

    5. Click DATA_PIPELINE.md in the file explorer sidebar to open the document.

    6. When working with Markdown documents in the Bob IDE, right-click the file tab and select Open Preview (keyboard shortcut Ctrl+Shift+V) to render the formatting. Headers, tables, and code blocks are far easier to read this way than in the raw source view.

    7. The document is now displayed in formatted preview mode. Headings and bullet points render cleanly, and so do the tables.

    8. Scroll through the document to review all five sections Bob produced, including the Mermaid flowchart at the end showing the full data pipeline from HTTP request to committed transaction.

    9. Although the IDE editor does not render Mermaid diagrams by default, Bob's chat panel can display them visually. Send the following prompt to render the diagram directly in the sidebar:

      Render the Mermaid diagram visually in the IBM Bob chat window.

    10. Bob renders the Mermaid flowchart as a visual diagram inside the chat panel. You can now read the complete data pipeline without needing a separate extension.

    11. Click the rendered diagram to open it in the main editor window at full size, where you can zoom in and explore the pipeline stages in detail.

    Extract the functional requirements

    1. Next, paste the following prompt into the chat input and hit Enter to have Bob extract and document every functional requirement from the codebase:

      Extract and document all functional requirements from the codebase:

- **Teller Operations**:

   - What can a teller do?
   - What information can they access?
   - What are the limitations?

- **Back-Office Operations**:

   - What administrative functions are available?
   - What privileged operations require BACKOFFICE role?

- **Business Rules**:

   - Overdraft limits and enforcement
   - Transfer validation rules
   - Fee reversal constraints

Format this as a structured requirements document with clear acceptance criteria.

    2. Bob begins working. Watch the Agentic Sidebar as it reads through the source files and builds the structured requirements document.

    3. Bob continues through the codebase, reading additional files to ensure all functional requirements are captured.

    4. Bob completes the task and confirms that FUNCTIONAL_REQUIREMENTS.md has been created in the project directory.

    5. The file explorer sidebar now shows FUNCTIONAL_REQUIREMENTS.md. Click the file to open it.

    6. Right-click the file tab and select Open Preview to view the formatted document with all sections rendered.

    7. Review the functional requirements document. It lists every supported operation — teller and back-office — along with the business rules that govern them.

    Document the invariants

    1. Paste the following prompt into the Agentic Sidebar and hit Enter to have Bob identify and document all system invariants and assumptions:

      Identify and document all system invariants and assumptions:

- **Data Invariants**: Rules that must always hold true in the database
- **Business Invariants**: Financial rules that cannot be violated
- **Security Invariants**: Access control rules that must be enforced
- **Technical Assumptions**: What the code assumes about its environment

For each invariant, explain:

- What the invariant is
- Where in the code it's enforced
- What could go wrong if violated

    2. Bob starts reading through the codebase to identify and document the invariants and assumptions.

    3. Bob continues reading files and extracting invariant rules as it works through the codebase.

    4. Bob completes the analysis and confirms that the invariants file has been written. Read through Bob's summary in the Agentic Sidebar to review its findings.

    5. Right-click the INVARIANTS.md file (or similarly named file) in the explorer sidebar and select Open Preview (Ctrl+Shift+V) to view the formatted document.

    6. Review the invariants document. Bob has catalogued every invariant it found in the codebase — data and business invariants as well as security and technical ones. For each, it records where the code enforces it and what would break if it were violated.

    iv. KEY TAKEAWAYS

    • Read-only analysis in Agent mode lets Bob explain an unfamiliar codebase without touching it.
    • Asking for documents rather than answers turns a conversation into persistent artifacts that later modules and later teammates can build upon.
    • The pasted-text pill is a review gate: expand it, confirm the prompt is intact, then send.
    • In a regulated setting, the invariants document is the most consequential of the four. It states what must always hold and where the code enforces it (and also states what breaks if a rule is violated.)
    • File names and the location of findings vary from run to run; what matters is that each analysis is complete and reviewed.

    With the application understood and documented, the next module transitions from reading to building. In Module 2 | Build, you will prove the existing teller client against the live GFM Bank backend, then have Bob generate a complete Carbon-based teller portal from a single specification.
