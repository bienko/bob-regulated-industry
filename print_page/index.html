    Regulated Industry with IBM Bob

    i. Regulated industries raise the bar for AI-assisted engineering

    Christopher Bienko (AI Enablement GTM Product Manager) introduces the Regulated Industry with IBM Bob curriculum for hands-on enablement. [4 min]

    Banking and insurance run on software that must satisfy an auditor as well as a user. Each capability has to be explainable. Each rule that governs money has to hold without exception. Each change has to leave a record of what was altered and by whom. These obligations shape how engineering teams in regulated sectors operate. They also define what an AI engineering partner must be able to do before it belongs in the workflow.

    This hands-on lab puts IBM Bob to work inside that setting. The application is GFM Bank, a demonstration core-banking system with a FastAPI backend. Role-based access control separates tellers from back-office staff, and a transaction engine enforces overdraft limits and reversal rules. Across three modules you will use Bob to build a documented understanding of that system. You will then generate a production-style teller interface on top of it. Finally you will find and remediate the security vulnerabilities hiding in its code. Each module produces the kind of durable, reviewable artifact a regulated environment expects.

    This lab is designed for the IBM sellers, partners, and technical practitioners who demonstrate Bob to clients in regulated sectors. Anyone comfortable with an IDE and a terminal can follow along.

    ii. What is IBM Bob?

    IBM Bob is an AI-powered software engineering partner that supports the entire development lifecycle. Where a traditional code-completion tool is anchored to the moment of writing code, Bob is designed to support the lifecycle around it. In this lab, Bob will:

    • Analyze an unfamiliar codebase and explain its architecture, roles, and business rules
    • Produce reference documentation, requirements, and invariants as persistent files
    • Generate a complete React front-end from a single specification, grounded in local design-system references
    • Diagnose runtime failures from a screenshot and a plain-language description
    • Audit code for security vulnerabilities, remediate them, and verify the result

    RECOMMENDED PREREQUISITE: CLIMBING THE AI MATURITY CURVE WITH IBM BOB LEVEL 3

    This course is best taken after the Climbing the AI Maturity Curve with IBM Bob Level 3 curriculum. It assumes those concepts are familiar ground: the Agentic Sidebar and its modes, the approval gates that keep the developer in control, and the review-before-trust habit that carried through every stage of that course. The material ahead builds directly upon that foundation.

    Bob operates directly within the development environment, so you keep complete visibility into every stage of the process. Bob does the work throughout this lab. Your job is to steer it with prompts and to judge the results before they are trusted.

    The GFM Bank backend itself runs remotely on IBM Cloud Code Engine, and the lab's clients and the front-end you build all connect to it over HTTPS. The system exercises the patterns that dominate real banking software:

    • OAuth2 authentication with TELLER and BACKOFFICE roles that differ in their permissions
    • A transfer engine with balance verification, overdraft handling, and a two-transaction debit/credit pattern
    • A data model that relates users and customers to their accounts and transactions
    • An audit trail of what is logged and stored for compliance

    Although GFM Bank is a demonstration system, it carries the same invariants and access rules that real core-banking platforms enforce. That is what makes it a credible stage for showing clients how Bob behaves under regulated-industry expectations.

    v. What you will build

    A WORD ON WORKING WITH GENERATIVE AI

    IBM Bob is powered by generative AI and LLMs, and a defining trait of these systems is that they are non-deterministic — unlike the deterministic tools most developers are accustomed to. In practice, that means the same prompt can produce different code from one run to the next. This is both a strength and a quirk of the technology, and it is something to work with rather than against.

    Precision is what tips the odds in your favor. The more clearly you describe what you want, the more closely Bob's output will mirror your intent; conversely, the smallest change in wording can meaningfully change the generated code. Throughout this lab, your results may differ from the solutions shown — and that is expected, not a defect. Whenever an output diverges, you have three good options: refine the prompt and try again, edit the generated code by hand, or simply proceed if the variation still compiles and runs. Human review remains essential at every step, and never more so than while you are still learning the tool.

    The understanding (Module 1 | Analyze). Using Agent mode with read-only tasks, you will have Bob produce four documents:

    • ARCHITECTURE.md
    • DATA_PIPELINE.md
    • FUNCTIONAL_REQUIREMENTS.md
    • An invariants document

    Together they describe the system's components and its request lifecycle. They also record every supported business operation and the rules that must never be violated.

    The application (Module 2 | Build). Using a single specification, Bob will generate a React teller portal built on the IBM Carbon Design System. It covers login and a dashboard with a live backend status indicator. It also covers the full set of teller operations, from balance inquiry to transfers. You will run it and sign in. You will then resolve the issues that surface with a screenshot and a sentence, reviewing Bob's fix each time.

    The assurance (Module 3 | Secure). Bob will scan the codebase for vulnerabilities and rank them by severity. It will document the five most critical with exploit scenarios and secure fixes. It will then apply the remediations and produce a verification report. A final run of the application confirms that the patches broke nothing.

    i. WHAT YOU WILL ANALYZE

    ii. WHY THIS MATTERS

    In a regulated environment, the questions an auditor asks of a system are the same questions an engineer must answer before changing it. What does each role have permission to do? Which rules govern a transfer, an overdraft, or a fee reversal? What must always remain true in the database, and where in the code is that guaranteed? Answering these by reading source files across a codebase is slow, and the answers rarely get written down.

    Bob compresses that discovery work into a handful of prompts. It writes the answers into documents for longevity and maintainability. Those documents serve two purposes at once. They give you the mental model needed for the build work in Module 2. They also form the first entries in the written record that regulated industries require of any system they operate.

    MODULE 2 | BUILD

    BUILDING THE CARBON TELLER FRONT-END

    i. WHAT YOU WILL BUILD

    Christopher Bienko (AI Enablement GTM Product Manager) provides an overview of the Build - Building the Carbon Teller Front-End module for the hands-on enablement. [2 min]

    AI MATURITY CURVE

    This chapter is Module 2 | Delegate at project scale. One specification produces an entire application, and an approval gate precedes every consequential step. The specification also grounds Bob deliberately. It requires that every Carbon prop name and token come from the local .d.ts files rather than from memory, which is the context-quality discipline of Module 4 | Scale & Extend applied to a design system. The result is code that maps onto the real backend and the real component library.

    The previous module left you with a documented understanding of GFM Bank. This module puts it to use. You first prove that the existing Python teller client can reach the live GFM Bank backend and return a real account balance. You then hand Bob a single, detailed specification and have it generate a complete React teller portal on the IBM Carbon Design System, grounded in the offline Carbon references shipped with the workspace. By the end of the chapter the portal is built and its dependencies are installed with a clean compile.

    ii. WHY THIS MATTERS

    A front-end for a regulated system has two obligations that ordinary web applications can afford to relax.

    1. It must call the real backend, with its real endpoints and roles and validation rules. A teller interface that drifts from the core banking API is a compliance problem in its own right.
    2. It must also present a consistent, accessible interface that an institution can standardize on, which is why the specification insists on the IBM Carbon Design System.

    Both obligations are met the same way: by grounding Bob in authoritative local sources before it writes a line of code. The Python clients from Module 1 describe the API as it actually is. The carbon-offline-reference folder describes the component library as it actually is. The specification directs Bob to read both, and the build you observe in this chapter is the consequence.

    iii. PROVING THE BACKEND CONNECTION

    ATTENTION: NON-DETERMINISTIC WORK AHEAD

    The sequence of commands and approvals in this section is specific to the run captured in the screenshots, which was performed on Windows with PowerShell.     ii. WHY THIS MATTERS

    Security review is where a regulated industry's expectations are most explicit. A finding is expected to carry a classification and a severity. It must name a location and an attack scenario. It must also propose a remediation and that remediation is expected to be verified rather than assumed. Producing that material by hand is slow work, which is why it so often arrives late, after the code has shipped.

    Bob compresses the cycle into a single session. It scans the code and ranks what it finds. It documents the findings and fixes them, then it verifies the result. Each stage is left behind as a file you can hand to an auditor for deeper review and inspection. Whether a finding is accepted, deferred, or challenged remains a judgment left to the human-in-the-loop. This practice mirrors the review-first, trust-later discipline of this entire hands-on lab applied to scenarios where the consequences for failure are highest.
